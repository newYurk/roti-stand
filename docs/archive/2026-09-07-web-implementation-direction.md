# Roti Stand — направление веб-реализации

Дата: 7 сентября 2026 года.

Документ собирает последние обсуждения веб-стека, структуры проекта, сохранения состояния и платформ. Это рабочая сводка с уточнениями, а не дословная стенограмма. Новое решение пользователя: **пока разрабатываем веб-реализацию**, платформы в порядке **iPhone → Android → Steam**.

## 1. Что принято, а что остаётся выбором

| Вопрос | Статус |
|---|---|
| Направление реализации | Web |
| Первая платформа | iPhone, публикация в App Store |
| Вторая платформа | Android, публикация в Google Play |
| Третья платформа | Steam |
| Сохранение игры | Обязательно |
| Управление | Палец на телефонах, мышь на компьютере |
| Поставка игры | Устанавливаемое приложение; веб-технологии не означают обязательный сайт |
| Рендерер полной игры | Не выбран: существующий Canvas 2D или GPU-рендер через библиотеку |
| Язык полной кодовой базы | JavaScript уже используется; TypeScript предложен для дальнейшей структуры |
| Мобильная оболочка | Capacitor — обсуждённый основной кандидат, не проверенная сборка проекта |
| Desktop-оболочка | Electron / Tauri — кандидаты; выбор не сделан |
| Хранилище | Файл, SQLite и IndexedDB обсуждены; окончательный выбор не сделан |
| Облачные сохранения | Возможное дополнение; обязательность не утверждена |
| Синхронизация iPhone ↔ Android ↔ Steam | Отдельная будущая функция, не обязательство первого релиза |
| Steam: поддерживаемые ОС | Нужно определить Windows/macOS/Linux отдельно |
| Минимальные устройства и версии ОС | Нужно определить |

Раньше обсуждался порядок iOS → Steam с возможным Android. Он заменён последней формулировкой пользователя: **iPhone → Android → Steam**.

## 2. Что означает Web для этой игры

Игровая логика выполняется на JavaScript; TypeScript при использовании преобразуется в JavaScript. Графика рисуется веб-API или библиотекой поверх них. В установленном приложении код, картинки и звуки могут находиться локально, поэтому основная игра может работать без интернета.

| Часть | Роль |
|---|---|
| HTML | Структура страницы и точка подключения приложения |
| CSS | Оформление и расположение HTML-интерфейса |
| JavaScript / TypeScript | Состояние мира, жесты, действия, симуляция, сохранения |
| Canvas 2D / GPU-рендер | Изображение теста, объектов и эффектов |
| Web Audio | Звук; нативный аудиопуть можно рассматривать при необходимости |
| Платформенная оболочка | Установка, жизненный цикл и доступ к функциям устройства |

Capacitor не переводит игру в Swift или C#. Он запускает веб-код в системном веб-компоненте и предоставляет связь с нативными API. На iOS это WKWebView, на Android — Android WebView.

Для Steam нужна настольная упаковка. Electron включает Chromium и Node.js; Tauri использует системные веб-компоненты и нативную оболочку. Их стоимость по памяти, размеру, интеграциям и поддержке нужно сравнивать применительно к игре.

## 3. Почему Web — полноценный кандидат

- Уже есть прототип теста и жестов, части которого можно использовать после переработки.
- Удобно быстро давать ссылку для ранних проверок механики.
- Общая модель приготовления и формат сохранения могут работать на всех платформах.
- Рисованный арт, текстуры, маски, анимации и деформируемые сетки доступны в веб-стеке.
- Можно подключать готовые библиотеки вместо самостоятельной реализации каждой системы.
- Нативные функции можно добавлять отдельно, не переписывая всё приложение.

Web не ограничен одним Canvas 2D и одним HTML-файлом. Обсуждены:

| Вариант | Что даёт | Что не решает автоматически |
|---|---|---|
| Текущий ручной Canvas 2D | Работающая база экспериментов | Архитектуру полной игры и редактор сцен |
| PixiJS | GPU-отрисовку, текстуры, контейнеры, маски, деформируемые сетки | Правила готовки, сохранения, платформенные сервисы |
| Phaser | Игровой фреймворк с готовыми системами | Специфическую физику роти |
| Phaser Editor | Визуальное редактирование сцен Phaser | Не является автоматически редактором проекта на PixiJS |

PixiJS и Phaser — альтернативы для оценки, а не обязательные библиотеки, которые надо подключить одновременно.

## 4. Цена выбора Web

- Нужно выбрать и согласовать рендерер, систему сцен, ассеты, звук и оболочки.
- Мобильные веб-компоненты и desktop-среду проверяем отдельно.
- Платформенные облака, гаптика и другие сервисы требуют интеграций.
- Удобство создания новых локаций зависит от выбранных инструментов редактирования.
- Складки, начинка, разрывы и прожарка — наша собственная модель независимо от стека.
- Перенос текущего прототипа в структуру полной игры всё равно потребует работы.

Предыдущие рейтинги «Web заведомо медленнее», «у Web нет редактора», «звук обязательно хуже» не подтверждены сравнительным тестом нашей игры. Это не основания для автоматического отказа от направления.

## 5. Роль index.html

**Полная игра не должна оставаться одним большим `index.html`.** В стенде так было удобно проверять гипотезы; в продукте логика разделяется на модули.

`index.html` остаётся небольшой точкой входа:

- метаданные страницы и параметры viewport;
- корневой элемент интерфейса / игрового экрана;
- подключение стилей и входного модуля;
- минимальное стартовое оформление при необходимости.

Физика теста, таблицы продуктов, сохранения и звук располагаются в отдельных файлах. Сборщик собирает необходимые ресурсы для браузера и платформенных оболочек.

Пример точки входа для проекта с инструментом сборки; это иллюстрация, не существующий файл репозитория:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Roti Stand</title>
  </head>
  <body>
    <div id="app"></div>
    <script type="module" src="/src/main.ts"></script>
  </body>
</html>
```

`index.html` и **IndexedDB** — разные вещи: первый запускает приложение, вторая является одним из вариантов хранения данных.

## 6. Предлагаемая структура проекта

Названия папок — рабочее предложение. Не требуется создавать пустую папку для каждой будущей функции.

| Путь | Содержание |
|---|---|
| `index.html` | Минимальная точка входа |
| `src/main.ts` | Инициализация приложения и соединение модулей |
| `src/game/` | Состояние мира, игровой цикл, время и события |
| `src/cooking/dough/` | Сетка, толщина, разрывы и складки |
| `src/cooking/frying/` | Нагрев, сушка, контакт и стороны прожарки |
| `src/cooking/actions/` | Прижать, шлёпнуть, перенести, добавить, сложить, перевернуть, разрезать |
| `src/cooking/tools/` | Поведение лопатки, резака и бутылок |
| `src/world/` | Локации, гости, отношения, взаимопомощь и обещания |
| `src/data/` | Описания продуктов, рецептов и персонажей |
| `src/input/` | Палец, мышь, распознавание жестов и отмена |
| `src/render/` | Отображение состояния игры выбранным рендерером |
| `src/ui/` | Очередь, диалоги, карта, блокнот, настройки |
| `src/audio/` | Звуки действий, жарки и атмосферы |
| `src/saves/` | Снимки, сериализация, валидация, версии и восстановление |
| `src/platform/` | Контракты хранилища, жизненного цикла, облаков и гаптики |
| `assets/` | Иллюстрации, текстуры, шрифты и записи звука |
| `tests/` | Проверки правил и сохранений, сценарии восстановления |
| `ios/`, `android/` | Нативные проекты, если выбран Capacitor |
| `desktop/` | Настольная упаковка, когда будет выбрана |

Расширение `.ts` соответствует предложению использовать TypeScript; оно не означает, что пользователь отдельно утвердила этот язык.

### Разделение ответственности

- Ввод распознаёт намерение игрока.
- Правила проверяют действие и изменяют состояние мира.
- Симуляция продолжает нагрев и другие процессы во времени.
- Рендер и звук отображают произошедшее.
- Сохранение получает согласованный снимок данных.
- Платформенная часть записывает данные в выбранное хранилище.

Canvas, DOM-элементы и аудиоузлы не должны быть самим форматом сохранения.

### Рецепты и свобода действий

Папка `recipes` содержит описания стандартного результата и подсказок. Она не должна становиться единственным разрешённым сценарием.

Возможность сложить край определяется гибкостью, геометрией и другими правилами. Положение на столе или на таве влияет на последствия. Состав блюда хранится в состоянии, а не только в имени класса вроде `BananaRoti`.

## 7. Ввод и инструменты

Общий смысл действия отделяем от устройства. Палец и мышь могут запускать одно `Press` или `Flip`, но использовать разные пороги расстояния, скорости и помощь при попадании.

В проверенном стенде уже есть общие обработчики начала, движения и отпускания; низкоуровневые события для касания и мыши различаются.

Сохраняем ориентиры обсуждения:

- шлепок — основная единица растяжки;
- перенос — жест-«запятая»;
- на таве прямое касание может означать действие лопатки;
- обязательное таскание лопатки за ручку не принято;
- прижим и переворот ещё требуют проверки;
- аппаратную силу нажатия не делаем обязательным входом;
- настройки мыши проверяем отдельно, не считаем её автоматически удобной;
- мультитач не требуется для базового приготовления.

## 8. Обязательное сохранение

Сохранение — обязанность самой игры. App Store распространяет приложение и не записывает игровой прогресс за нас.

### Что сохраняем

| Блок | Данные |
|---|---|
| Настройки | Язык, звук, раскладка управления |
| Долгосрочный прогресс | Отношения, обещания, открытые продукты, изменения тележки |
| Текущий день | Время, локация, очередь, оставшиеся продукты, события |
| Заказ | Посетитель и его просьба |
| Роти | Геометрия, толщина, разрывы, складки, начинка, прожарка обеих сторон, топпинги и нарезка |
| Служебные поля | Версия формата, ревизия снимка, версия игры при необходимости |

Схематический пример, не окончательный контракт:

```json
{
  "saveVersion": 1,
  "revision": 42,
  "world": {},
  "day": {},
  "inventory": {},
  "activeOrder": {},
  "activeRoti": {
    "location": "tava",
    "geometry": {},
    "ingredients": [],
    "cooking": {}
  }
}
```

Числовые шкалы отношений, конкретные имена полей и формат геометрии из прежних примеров не являются принятыми дизайнерскими решениями.

### Как сохранять тесто

Обсуждены три подхода:

| Подход | Плюс | Ограничение |
|---|---|---|
| Снимок текущих данных | Прямое восстановление | Формат зависит от модели теста |
| Журнал действий | Полезен для диагностики | Для точного replay нужны начальное состояние, управляемая случайность и время |
| Снимок плюс журнал | Надёжное продолжение и дополнительная диагностика | Две разные функции, которые нужно поддерживать |

Предложение: сохранять снимок мира и активного роти; журнал использовать для QA, а не как единственный источник восстановления.

Тысяча узлов сама по себе не требует базы данных: массивы можно записывать файлом или в базу. Итоговый размер зависит от количества полей и кодирования; прежнее «десятки килобайт» было оценкой порядка, а не замером готового сохранения.

## 9. Варианты хранилища

**Файл через Capacitor — не единственный способ.** Окончательный выбор пока открыт.

| Вариант | Подходит для | Работа, которую берём на себя |
|---|---|---|
| JSON / бинарный файл | Цельный снимок дня и роти | Проверка, резервирование, версии и восстановление |
| SQLite | Связанные записи и транзакционные изменения | Плагин, схема базы, миграции и сборки |
| IndexedDB | Данные в веб-среде, в том числе браузерный прототип | Проверка жизненного цикла, хранилища и поведения оболочек |
| Capacitor Preferences | Небольшие настройки | Не использовать как универсальное место для всей сложной модели |
| Облачное хранилище | Перенос между устройствами | Авторизация, конфликты, сеть и локальный режим |

Файл удобен, если мир записывается цельным снимком. SQLite полезна, если делаем независимые связанные записи, которым нужна общая транзакция. IndexedDB остаётся возможным вариантом, но установленную игру нужно проверить в реальных мобильных оболочках.

`localStorage` используется в стенде для отдельных данных. Это не принятое хранилище полной игры.

При выборе файлового пути `@capacitor/filesystem` предоставляет запись и чтение из нативной файловой системы. Для iOS выбирается постоянный каталог приложения, не кэш. Приложение не обязано просить игрока выбирать файл вручную.

## 10. Когда и как сохранять

Предложенные точки:

- завершённое действие готовки;
- завершённый заказ и разговор;
- изменение обещания или локации;
- изменение настроек;
- периодически во время жарки;
- уход в фон как дополнительный повод.

**Одних действий недостаточно:** роти жарится даже без касаний. **Одного события закрытия тоже недостаточно:** ОС может остановить процесс прежде, чем запись завершится.

Записи ставим в последовательную очередь. Снимок не должен меняться в процессе сериализации. Состояние заказа, инвентаря и роти сохраняется согласованно: нельзя восстановить потраченное яйцо и одновременно получить роти без этой траты.

Логические блоки `world` и `active_session` не обязаны быть отдельными файлами. Независимая запись связанных файлов без общего механизма согласованности создаёт риск противоречий.

### Надёжность

Обсуждались два файловых подхода:

1. Временный файл, проверка, надёжная замена основного с резервной копией.
2. Чередование двух слотов: новая ревизия записывается в один, предыдущая остаётся в другом. При загрузке выбирается последнее корректное состояние.

Это альтернативы, а не требование одновременно реализовать обе. Нельзя объявлять произвольную последовательность операций плагина атомарной без проверки её гарантий.

Для SQLite соответствующие связанные изменения выполняются транзакцией. Любому подходу нужны проверка данных, версия формата и политика восстановления.

### Обновление игры

Сохранение содержит `saveVersion`. При изменении структуры определяются миграции. Повреждённое сохранение не должно молча обнулять всё прохождение, если сохранилась исправная копия. Сохранение более новой неизвестной версии тоже нельзя безусловно перезаписывать.

## 11. Продолжение незаконченного приготовления

Предложение для мобильной игры:

- восстанавливать день, заказ, ингредиенты и роти;
- отменять старое касание;
- не продолжать жарку за время отсутствия игрока;
- возвращаться на паузе, затем возобновлять ввод и звук;
- для короткого перехода вроде полёта использовать целостное состояние до или после перехода.

Понятие «устойчивое состояние» не означает, что горячее роти перестало меняться. Оно означает пригодный для восстановления согласованный снимок.

Политика для незавершённой складки и длительного жеста ещё требует решения. Автоматически перемещать всё в «безопасное место» без сохранённого правила нельзя: это может изменить результат приготовления.

## 12. Облака и синхронизация

Локальное сохранение и облачная синхронизация — разные функции.

| Платформа | Локально | Возможное облачное дополнение |
|---|---|---|
| iPhone | Файл / база в приложении | iCloud / CloudKit через интеграцию |
| Android | Файл / база в приложении | Google Play Games Saved Games |
| Steam | Файл / база в пользовательских данных | Steam Cloud |

Платформенные облака не объединяются автоматически. Общий формат данных полезен для будущего переноса, но сам по себе не даёт синхронизации iPhone ↔ Android ↔ Steam.

Для межплатформенной синхронизации потребуются общее облачное решение и способ идентификации пользователя, разрешение конфликтов и совместимость версий. Это можно делать собственными средствами или подходящим сервисом; собственный сервер не единственная возможность.

Локальное сохранение не гарантирует восстановление после удаления приложения или замены телефона. Резервная копия устройства и игровая облачная синхронизация также не одно и то же.

## 13. Что известно о текущем стенде

Состояние по проверке исходника в обсуждении; не новая проверка последнего коммита:

- один HTML-файл, JavaScript, Canvas 2D и Web Audio;
- сетка 38×38, обрезанная до круга, около тысячи узлов;
- восемь подшагов расчёта;
- расплющивание, шлепки и перенос реализованы;
- на таве есть модель сушки и прожарки одной стороны;
- при переносе деформация временно заморожена;
- жесты жарки на таве ещё не реализованы;
- сложные слои и начинка отсутствуют;
- полного восстановления роти после перезапуска нет.

Найдена ошибка счётчика FPS: ограниченное значение `dt` используется для оценки прошедшего времени. При долгих кадрах это завышает показатель. Ошибка была обнаружена, но исправление в рамках обсуждения не выполнялось.

M3 показывал 59,7 FPS в тесте одного спрайта 160×160; это не доказательство запаса полной сцены. Некоторые варианты стенда отрисовывают сцену шириной 80 или 224 пикселя и масштабируют её. Их показатели нельзя напрямую переносить на утверждённый рисованный арт.

## 14. Проверки выбранного веб-направления

Развиваем существующую сцену, а не создаём ещё один дубликат стенда.

### Сначала iPhone

Показательная сцена: лист → начинка → четыре складки → прижим → переворот; утверждённый арт и одновременно несколько звуковых слоёв. Добавить запись и восстановление.

Проверить:

- время кадров и длинные кадры отдельно от ограниченного шага симуляции;
- расходы симуляции, рендера и памяти;
- задержку жест→звук;
- 10–15 минут работы и нагрев устройства;
- фон, блокировку, возврат и принудительное завершение;
- восстановление после двух складок и продолжение заказа;
- отсутствие двойного расхода или возврата ингредиентов;
- повреждённую запись, старую версию формата и нехватку места.

### Затем Android

Та же логика, но отдельная сборка и проверки на выбранных устройствах: ввод, звук, системная навигация, фон, сохранение, разрешение экрана и производительность.

### Затем Steam

Выбор настольной оболочки и поддерживаемых ОС. Проверка мыши, размеров окна, сохранений и настольного аудиопути. Steam Cloud — отдельное решение.

Не нужно переписывать модель только потому, что один вариант Canvas-отрисовки оказался медленным. Сначала определяем конкретное узкое место; GPU-рендер, изменение алгоритма и нативный модуль — разные способы его устранения.

## 15. Следующие решения по направлению

1. Выбрать конкретную веб-конфигурацию: язык, рендерер, аудио и упаковка.
2. Определить минимальный iPhone для первой проверки.
3. Разделить код прототипа на модули без потери ощущения жестов.
4. Определить контракт снимка мира и активного роти.
5. Выбрать файл, SQLite или IndexedDB по требованиям восстановления.
6. Реализовать показательный цикл со складкой и сохранением.
7. Проверить iPhone, затем Android, затем настольную сборку для Steam.

Решение «пока Web» принято. Полная пригодность конкретной конфигурации подтверждается проверками, а не престижностью языка или названием движка.
